# WoW Live

A Windows app for Mythic+ keys and raid pulls, read live from the game's combat log (README.md).

- The `Makefile` wraps the commands below: `make check` (CI's checks, except its spec diff and Windows job), `make app`, `make swag`, `make ref`, `make release` (asks twice, then tags main with the next patch and pushes the tag).
- `backend/` is one Go module (`clients/` outside systems, `models/` types and interfaces, `service/` the rules, `controller/` the Gin API with swaggo annotations, `app/` the wiring, `cmd/` entry points). Run `gofmt`, `go vet ./...`, `golangci-lint run` (`.golangci.yml`: 120 columns, `errcheck`, `staticcheck`, `unused`) and `go test ./...` there; after changing an endpoint or its types, run `swag init -g cmd/site/main.go -o docs --parseInternal`.
- `frontend/` is React + Vite + TypeScript: `api.ts` is the only file that knows URLs, and values the backend owns come from the API. Run `npm run lint` (ESLint holds the 120 columns), `npm test` and `npm run build`. No Prettier config: single quotes, no semicolons, never reformat whole files.
- The app (`backend/cmd/app`, Wails v3, Windows only) is built with `bash backend/cmd/app/build.sh`. Before restarting a running copy, check the newest combat log for a key in progress. A copy started from Claude's shell writes its data into the Claude app's package folder, so let the owner start it.
- The rules' names live once in `mplus.toml` (M+) and `raid-rules.toml` (raid), the dungeon facts in `reference/mplus-dungeons.json` (written by `go run ./cmd/mplusref`) and the raid's boss mechanics in `reference/raid-bosses.json` (`go run ./cmd/raidref`, from the hand-kept `reference/raid-mechanics.toml`, whose spell IDs are the hit's, aura's or cast's the app matches, checked against logs); nothing hardcodes a guild, realm or character. A raid pull runs on the log tracker's per-fight run (`service/raid.go`), so deaths, defensives, meters, must-stops, dispels and the replay's track share the M+ code; its lanes and "Fix next pull" suggestions are `service/raid_review.go`. The pages share their UI too: `FightMeters.tsx` (the meter cards that follow the replay and drill into a player) and `fightTabs` (`KeyTabs.tsx`, the bottom tabs). Improve those, not one page's copy.
- Recaps (a player's last `[big_hits] recap_seconds` before a death or big hit) and big hits are `service/hits.go`, saved on the track (`Recaps`) and the key (`BigHits`); `HitRecap.tsx` shows a recap everywhere (tabs, overlay). Health comes from the advanced-logging block, which names the target on spell hits and heals but the attacker on melee swings.
- A player's review against top logs is `service/compare.go` (`Comparer`: the stored review, the 20 nearest logs, `similarKeys`) over the pure `compare_build.go` (`buildCompare`, `verdict`); the Warcraft Logs reads are `clients/wcl/compare.go` (about 8 points a log; `Comparer` refuses under `minComparePoints` in `service/compare.go`). The spec's own rules are `spec-rules.toml` (`service/spec_rules.go`, run on the player's own track only, since reading the top logs' events would multiply the points). The player and the top logs both come in as `models.RankedPlayer`, so a saved key or pull and a ranked report read alike.
- Every hover is `Tip.tsx`'s box (`TipHost`, mounted once in `main.tsx`): put `tip(text, head)` or `spellTip(abilityName)` (`tipAttrs.ts`) on an element, never a `title=`; abilities in lists are `Spell`/`Cover` (`Spell.tsx`). A spell's text is `service.Spells` (spell ID from `LogTracker.SpellID`, the one the ability was cast by, read from Wowhead's tooltip by `wowhead.Client.Spell`), so the log must have shown the ability since the app started.
- A player review's talents (`CompareTalents`, `talentCompare` in `compare_build.go`) are the saved key's or pull's `Talents` (COMBATANT_INFO's `[(node,entry,rank)]`, read by `talentPicks`) against each top log's `combatantinfo` event (`wcl.playerTalents`, one cheap query a fight, kept for good); the tree's places come from `reference/talent-trees.json` (`go run ./cmd/talentref`, from Raidbots; built into the app by `build.sh`), served by `GET /api/talents/{specID}` and drawn by `TalentTree.tsx` over `readTree` (`talents.ts`), with icons from `GET /api/icons/{name}` (`wowhead.Client.Icon`, kept in the cache; the page's CSP allows no other image host) and the talent's hover from `GET /api/spells?id=` (`Spells.ReferenceSpell` answers a mob's or a talent's spell ID only). A review reads its top logs `compareWorkers` at a time (`readTop`); the character listing walks report pages ahead (`recentReports`) and asks reports' fights `reportsPerQuery` at a time. A dungeon review leaves out raid-only buffs (`LogTracker.RaidOnlyBuff`, the Vantus patterns in `raid-rules.toml`). Buffs that are an always-on talent (top logs 99%+) are left off the buff list (`passiveNames`). Warcraft Logs lists a buff once per spell ID, so a buff is one row by name, never a sum (`buffUptimes`, `rankedPlayer`).
- Raid buff gaps live in `service/ready.go` (`buffChanged`, `buffGaps`), and a key's track keeps casts and ability stretches like a pull's (`abilitySampler` in `service/track.go`). *Read old logs* (`Site.Learn`) skips logs listed in the cache's `learned.json` under the same `readerVersion` (`app/app.go`): bump it whenever a change saves new key, pull or track fields, so the owner's next read fills them in. Some buffs (Vantus Runes) are hidden auras the log never names: match those by spell ID in the rules, not by name.
- Log reading streams (`combatlog.EachLine(io.Reader)`, `EachLineIn`, `EachZippedLine`; `Parse` for Follow's backlog) and keeps one string per line, since the tracker keeps names cut from it. Archived logs are zips in `<log folder>\WoW Live archive\` (`combatlog.Archive`); which can be archived or deleted is `service/logs.go`, and `Site.logJob` lets one read, archive or delete run at a time. A change that should save the same keys and pulls is checked by rebuilding them with `go run ./cmd/site --learn` on a fresh cache before and after: the files must match byte for byte (a track is `.json.gz`: compare it decoded), so build saved lists from sorted keys, never in map order.
- The tracker keeps saved keys and pulls *slim* (`Slim`: no `Abilities`, `Taken`, `Targets`; `LogTracker.history` / `pulls`) so a long history stays small. Anything shown to the user or saved reads the whole fight with `whole(store, fight)` (`service/fights.go`): a page, a review, the runs it compares with, a link. Never read those lists from `history` or `pulls` directly; `Folder.Save` refuses a slim fight, and `TakenByAbility` / `HasAbilities` answer what a list or the Recap needs. The golden files in `service/testdata` (`go test ./service -run Golden -update`) show a change to what is saved.
- The Recap tab is `service/recap.go` (pure `buildRecap` over the tracker's in-memory keys and pulls, Mythic+ and raid as two halves). The top bar's character filters every list through `loggedBy` in `service/characters.go` (the logger and its realm from `Key.Realms` / `RaidPull.Realms`); keep new per-character lists on it. Local keys and pulls are linked to the owner's Warcraft Logs reports by `ReportLinks` (`service/wclimport.go`) whenever the import lists reports, and keep that `Report` when the log is read again.
- *Import from Warcraft Logs* (`service.Importer` in `service/wclimporter.go`, fights picked by `PickFights` in `service/wclimport.go`) writes each Warcraft Logs fight back as a combat log zip (`wcl.ImportFight`, the converter in `clients/wcl/combatlog.go`) and reads it with the same reader, into a tracker of its own tagged by `SetSource`, so imported keys and pulls carry `Report` and `Imported`. Fix a difference from the game's log in the converter, never in the tracker; `go run ./cmd/site --wcl-fight CODE#N` writes one fight to compare.
- The game writes its combat log in batches as fights start and end (Nov 10: 2:45 of a boss fight in one write), and logs no end for a key the party left. So nothing is live inside a fight or while a party stands around before a key, and a silent log can be a long fight: `quietMS` and `LogTracker.Abandon` in `service/mplus.go`, which leaves a raid pull alone (a fight can outlast any silence).
- Mythic+ routes: planned routes are `service/routes.go` over `clients/routestore`; MDT export strings (`!~MDT2~`, raw Deflate over CBOR) are `clients/mdt/route.go` and MDT's saved routes `clients/mdt/saves.go`; the enemies on each map come from `cmd/mplusref`; `service/route_progress.go` matches a key's kills to a route (`MatchKills`) and gives each route pull its live state (`markPulls`: done, next, later, missed; `livePullsAhead`, `behindPct`), which `RouteMap` draws and `KeyRoute` lists. Mob health at a key level is `service/mobs.go` (Keystone.guru's rule, checked against a +17 log): change its constants, never the page. Patrols are Keystone.guru's `enemy_patrols.json` put in log yards by `service.RoutePatrols`. A route's drawings are checked by `checkDrawings` against `drawingLimits` (served as `RouteView.Limits`); in MDT strings `Routes.importDrawings` / `exportDrawings` place them through each floor's `MDTPlane` (fitted by `service.MDTPlanes` in `cmd/mplusref`), and what an import can't place stays in `Route.MDTDrawings` for the export.
- The Home tab (`Home.tsx`, `guide.ts`, `StoragePanel.tsx`) holds the first-run guide (`Settings.SetupDone`), status and data management; the log list is `CombatLogs.tsx` over `service/logs.go`, which lists the game's logs, archived zips and Warcraft Logs imports (delete-only) and holds the auto rule (`service.AutoPicks`, run by `Site.Tidy` at start and after each key or pull; an import's age is when it was imported). Folder sizes are `clients/cachefile/size.go` (`GET /api/storage`). Loading never flashes: `index.html`'s splash, `useDelayed` and `Skeleton`; a waiting page is `WaitingCard`.
- The full review page (`ReviewPage.tsx`, routed by `main.tsx` from `/review/{mplus|raid}/{start}`) takes a key or a pull as one `Fight` and shares its tabs and components with the key and raid pages; add a tab there, not a copy. The Player tab reads the track's per-player `Casts` and `Buffs` (`events.ts`: `cooldownLanes`, `buffUptimes`). `reviewURL` and `popOutReview` (`api.ts`) are the only places that build its address and open it in a window (the app's `open-review` event, `popOut` in `cmd/app/windows.go`).
- The overlay's settings are `models.OverlaySettings` (validated in `service/settings.go`, which also holds `overlayPresets`); `overlayIds`/`overlayColumn` (`meterColumns.ts`) build a card's columns for the M+ (`Overlay.tsx`) and raid (`RaidOverlayCard`) pages alike, and `useFreshDeath` shows a death's recap without a click. The window keeps its content's shape: the page reports it (`overlayShape`) and `holdShape` (`cmd/app/windows.go`) sets the height; Ctrl+Alt+H (`hideOverlay`) hides it until the next key or pull. Only cards and bars set the overlay's width: a line of text (`p`, `li`, `.row-button`, `.overlay-clock` in `.overlay-fit`) wraps to it (`contain: inline-size`), so one long phrase never shrinks the zoom; a death line is a `.death-button`. Settings' Preview buttons make the overlay show `overlayDemo.ts`'s dummy key or raid pull (the `overlay-preview` event; a start of `DEMO_START` reads its recaps from there).
- The Sim tab (desktop app only; `Sim.tsx` over `SimGear.tsx` (the gear by slot), `SimItem.tsx` / `simItems.ts` (item icons from `GET /api/sim/items`, `service.Items` over `wowhead.Client.Item`, asked `SimChoices.MaxItemLookups` at a time), `SimResult.tsx`, `simOptions.ts`) runs SimulationCraft: `clients/simc` installs `simc.exe` from this repo's `simc-engine` release over HTTPS, checked against the sha256 in its `engine.json` plus `MZ` and banner checks (or copies a `simc.exe` the owner names); `.github/workflows/simc.yml` rebuilds that release weekly from the official nightly in simulationcraft/simc-publish's Actions artifacts, checking their sha256, and runs only on `main` (simulationcraft.org itself is plain HTTP with no checksum, so the app never uses it), `service/simprofile.go` reads the pasted `/simc` export into validated fields (`ParseSimC`, `SimInput`: the export is untrusted, simc's `input=`/`output=` lines never reach the file, so each request re-parses the text), `service/sim.go` runs one sim at a time and maps json2, `simgear.go` (Top Gear, `maxCombos`; whether a bag weapon is two-handed is asked of Wowhead, `wowhead.Client.TwoHanded`) and `simdrops.go` (Droptimizer, `maxDrops`) add profilesets, and `controller/sim.go` serves `/api/sim`. Drop data is `reference/sim-drops.json` (`go run ./cmd/simref`, embedded in the app) with item levels in the hand-kept `reference/sim-drops.toml`. Besides the gear a request names `Consumables` (`flask=`, `food=`, `potion=`, `augmentation=`, `temporary_enchant=main_hand:` lines), an Omnium Folio (`omnium_talents=entryID:1/...`, entry IDs of Raidbots' tree; simc ignores the rank), Top Gear `Variants` (`service/simoptions.go`: a changed copy of a picked item, with its upgrade-track bonus ID swapped, `SocketBonus` added, a `gem_id` and an `enchant_id`, joining the candidates before `gearGroups` counts them) and `Consumables` as lists per kind (one value is a baseline line, two or more of a kind are compared: `compareCombos` makes every combination of the compared kinds as profilesets, `gearCombo.line`; a Quick Sim's rows are `SimResult.Options`, the others cross each combination with every value, `withCompare`, and name it in `SimCombo.Consumable`); a Droptimizer's `MaxUpgrade` sims each drop fully upgraded: at the top rank of its upgrade track (`maxedLevel`), plus `venomstoneLevels` on a Hero or Myth weapon, trinket or neck (Ascendant Venomstones: Myth 334 to 341). Every name that reaches simc's input is looked up in `reference/sim-options.json` (`go run ./cmd/simoptref` from Raidbots' public game data, read through `clients/raidbots` like `cmd/talentref`, which refuses a consumable name that isn't `[a-z0-9_]`; embedded in the app; `GET /api/sim/options`), never copied from the request, and `POST /api/sim/plan` counts a Top Gear request's combinations (`comboCount`, refused by `comboRefusal` in the same words as Start) and names its variants (`SimPlan.Notes`) for the page's cost line and chips (`simPlan.ts`). Tests use an in-process fake engine (`fakeEngine`).
- Changes go through a branch (`feat/…`, `fix/…`, `chore/…`) and a PR; commit, push and open it only when the owner says so. What each PR changed goes under `[Unreleased]` in CHANGELOG.md. The Store's MSIX builds only on a `v*` tag or by hand.
