# WoW Live

A Windows app for Mythic+ keys and raid pulls, read live from the game's combat log (README.md).

- The `Makefile` wraps the commands below: `make check` (what CI runs), `make app`, `make swag`, `make ref`, `make release` (asks twice, then tags main with the next patch and pushes the tag).
- `backend/` is one Go module (`clients/` outside systems, `models/` types and interfaces, `service/` the rules, `controller/` the Gin API with swaggo annotations, `app/` the wiring, `cmd/` entry points). Run `gofmt`, `go vet ./...` and `go test ./...` there; after changing an endpoint or its types, run `swag init -g cmd/site/main.go -o docs --parseInternal`.
- `frontend/` is React + Vite + TypeScript: `api.ts` is the only file that knows URLs, and values the backend owns come from the API. Run `npm run lint`, `npm test` and `npm run build`. No Prettier config: single quotes, no semicolons, 120 columns, never reformat whole files.
- The app (`backend/cmd/app`, Wails v3, Windows only) is built with `bash backend/cmd/app/build.sh`. Before restarting a running copy, check the newest combat log for a key in progress. A copy started from Claude's shell writes its data into the Claude app's package folder, so let the owner start it.
- The rules' names live once in `mplus.toml` (M+) and `raid-rules.toml` (raid), the dungeon facts in `reference/mplus-dungeons.json` (written by `go run ./cmd/mplusref`) and the raid's boss mechanics in `reference/raid-bosses.json` (`go run ./cmd/raidref`, from the hand-kept `reference/raid-mechanics.toml`, whose spell IDs are the hit's, aura's or cast's the app matches, checked against logs); nothing hardcodes a guild, realm or character. A raid pull runs on the log tracker's per-fight run (`service/raid.go`), so deaths, defensives, meters, must-stops, dispels and the replay's track share the M+ code; its lanes and "Fix next pull" suggestions are `service/raid_review.go`. The pages share their UI too: `FightMeters.tsx` (the meter cards that follow the replay and drill into a player) and `fightTabs` (`KeyTabs.tsx`, the bottom tabs). Improve those, not one page's copy.
- Recaps (a player's last `[big_hits] recap_seconds` before a death or big hit) and big hits are `service/hits.go`, saved on the track (`Recaps`) and the key (`BigHits`); `HitRecap.tsx` shows a recap everywhere (tabs, overlay). Health comes from the advanced-logging block, which names the target on spell hits and heals but the attacker on melee swings.
- Every hover is `Tip.tsx`'s box (`TipHost`, mounted once in `main.tsx`): put `tip(text, head)` or `spellTip(abilityName)` (`tipAttrs.ts`) on an element, never a `title=`; abilities in lists are `Spell`/`Cover` (`Spell.tsx`). A spell's text is `service.Spells` (spell ID from `LogTracker.SpellID`, the one the ability was cast by, read from Wowhead's tooltip by `wowhead.Client.Spell`), so the log must have shown the ability since the app started.
- Raid buff gaps live in `service/ready.go` (`buffChanged`, `buffGaps`), and a key's track keeps casts and ability stretches like a pull's (`abilitySampler` in `service/track.go`). *Read old logs* (`Site.Learn`) skips logs listed in the cache's `learned.json` under the same `readerVersion` (`app/app.go`): bump it whenever a change saves new key, pull or track fields, so the owner's next read fills them in. Some buffs (Vantus Runes) are hidden auras the log never names: match those by spell ID in the rules, not by name.
- Log reading streams (`combatlog.EachLine(io.Reader)`, `EachLineIn`, `EachZippedLine`; `Parse` for Follow's backlog) and keeps one string per line, since the tracker keeps names cut from it. Archived logs are zips in `<log folder>\WoW Live archive\` (`combatlog.Archive`); which can be archived or deleted is `service/logs.go`, and `Site.logJob` lets one read, archive or delete run at a time. A change that should save the same keys and pulls is checked by rebuilding them with `go run ./cmd/site --learn` on a fresh cache before and after: the files must match byte for byte, so build saved lists from sorted keys, never in map order.
- The Recap tab is `service/recap.go` (pure `buildRecap` over the tracker's in-memory keys and pulls, Mythic+ and raid as two halves). The top bar's character filters every list through `loggedBy` in `service/characters.go` (the logger and its realm from `Key.Realms` / `RaidPull.Realms`); keep new per-character lists on it. Local keys and pulls are linked to the owner's Warcraft Logs reports by `ReportLinks` (`service/wclimport.go`) whenever the import lists reports, and keep that `Report` when the log is read again.
- *Import from Warcraft Logs* (`service.Importer` in `service/wclimporter.go`, fights picked by `PickFights` in `service/wclimport.go`) writes each Warcraft Logs fight back as a combat log zip (`wcl.ImportFight`, the converter in `clients/wcl/combatlog.go`) and reads it with the same reader, into a tracker of its own tagged by `SetSource`, so imported keys and pulls carry `Report` and `Imported`. Fix a difference from the game's log in the converter, never in the tracker; `go run ./cmd/site --wcl-fight CODE#N` writes one fight to compare.
- The game writes its combat log in batches as fights start and end (Nov 10: 2:45 of a boss fight in one write), and logs no end for a key the party left. So nothing is live inside a fight or while a party stands around before a key, and a silent log can be a long fight: `quietMS` and `LogTracker.Abandon` in `service/mplus.go`, which leaves a raid pull alone (a fight can outlast any silence).
- The Home tab (`Home.tsx`, `guide.ts`, `StoragePanel.tsx`) holds the first-run guide (`Settings.SetupDone`), status and data management; the log list is `CombatLogs.tsx` over `service/logs.go`, which lists the game's logs, archived zips and Warcraft Logs imports (delete-only) and holds the auto rule (`service.AutoPicks`, run by `Site.Tidy` at start and after each key or pull; an import's age is when it was imported). Folder sizes are `service/storage.go` (`GET /api/storage`). Loading never flashes: `index.html`'s splash, `useDelayed` and `Skeleton`; a waiting page is `WaitingCard`.
- Changes go through a branch (`feat/…`, `fix/…`, `chore/…`) and a PR; commit, push and open it only when the owner says so. What each PR changed goes under `[Unreleased]` in CHANGELOG.md. The Store's MSIX builds only on a `v*` tag or by hand.
